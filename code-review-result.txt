## 问题列表

### 🔴 [严重:高] SqlEditor.tsx 注册守卫实际在组件函数体内，切 tab 泄漏 provider

**文件**: src/renderer/components/SqlEditor.tsx 第 215-217 行

**问题描述**: completionProviderRegistered 和 globalCompletionDisposable 声明在**组件函数体内**（位于 useEffect 与 beforeMount 之间），虽然注释写着"模块级补全 provider 注册守卫"，但实际每次渲染重新初始化为 false 和 null。注册守卫失效。

**影响**:
1. 切换 tab 时（key={tab.id} 不同 → React 卸载旧实例、挂载新实例），beforeMount 重新执行 → 注册新的 completion provider
2. 旧 provider 的 dispose() 从未被调用（globalCompletionDisposable 被新实例覆盖，旧引用丢失）
3. **内存泄漏累积**：每次切换 tab 都注册一个新的 completionItemProvider，且无法被 cleanup
4. 修复注释声称"修复泄漏"但实际未修复

**修复方案**: 将这两个变量移到组件外层（模块级作用域），或者在 useEffect(() => { ... return () => disposable.dispose() }, []) 中管理注册。

### 🟡 [严重:中] query:cancel 取消机制无效（半成品）

**文件**: src/main/services/query-service.ts 第 194-204 行
**文件**: src/main/ipc.ts 第 142-176 行

**问题描述**: 取消机制存在三个层面的问题：

1. **AbortController 仅检查入口，不取消执行中的查询**:
   - QueryService.run 中 signal?.aborted 仅在语句执行前检查一次（第 199 行）
   - 真正执行查询的 this.executor(sql)（第 200 行）不接收 signal
   - ConnectionManager.executeMany 也不检查 signal
   - 所以 abortController.abort() 只能取消"尚未开始执行"的查询，不能中断正在跑的 SQL

2. **渲染进程完全无法调用 query:cancel**:
   - grep 确认渲染进程**没有任何地方**调用 query:cancel
   - query:execute 的响应 QueryResult 中不包含 queryId 字段
   - 渲染进程无法构造 query:cancel 所需的 {connectionId, queryId} 参数

3. **测试未覆盖**: 仅 ipc-contract.test.ts 检查了 channel 存在性，无功能测试

**修复方案**: 需要 MySQL 连接层面的 KILL QUERY 或 mysql2 的 connection.destroy() 才能真正取消正在执行的查询。

### 🟡 [严重:中] schema-cache.ts 中 SQL 拼接未转义反引号（与 ipc.ts 不一致）

**文件**: src/main/services/schema-cache.ts 第 34-36 行
**对比**: src/main/ipc.ts 第 128 行（已修复）

**问题描述**: SCHEMA_SQL 中 listTables、getColumns、getDdl 直接字符串拼接：
  listTables: (db) => SHOW FULL TABLES FROM `db`
  getColumns: (db, table) => SHOW FULL COLUMNS FROM `table` FROM `db`
  getDdl: (db, table) => SHOW CREATE TABLE `db`.`table`

如果数据库名或表名包含反引号，会导致 SQL 语法错误或注入。虽然攻击面较小（需要能创建含反引号名称的数据库/表），但 ipc.ts 的 schema:dataPreview 已经用 (s) => s.replace(/`/g, '``') 修复了，schema-cache 作为同类代码未同步修复，是不一致的缺陷。

**修复方案**: 对 SCHEMA_SQL 中各函数内的 db/table 参数做反引号转义：
  const esc = (s) => s.replace(/`/g, '``');
  listTables: (db) => `SHOW FULL TABLES FROM \`${esc(db)}\``

### 🟡 [严重:中] SqlEditor.tsx 快捷键 effect 依赖竞态，首次挂载可能不注册

**文件**: src/renderer/components/SqlEditor.tsx 第 193-213 行

**问题描述**: 快捷键注册 effect 依赖 [monacoRef.current, editorRef.current]。首次渲染时：
1. 子组件（@monaco-editor/react 内部）的 onMount 异步调用（微任务），在父组件同步 effect 之后
2. 首次 effect 运行时 editorRef.current 和 monacoRef.current 均为 null → return 提前退出
3. ref 变化不触发 re-render（ref.current 赋值不是响应式操作）
4. 快捷键注册依赖于**其他原因**触发的 re-render（如输入 SQL 触发 onSqlChange → zustand 更新 → App re-render）

**竞态窗口**: 打开 app 后立即按 Ctrl+Enter，可能无响应（需要先输入内容触发 re-render）

**修复方案**: 将快捷键注册放在 onMount 回调中（此时 editor/monaco 已就绪），或使用 useState 记录 editor 就绪状态作为依赖。

### 🟡 [严重:低] fetchSchemaSnapshot 竞态（无 requestId 守卫）

**文件**: src/renderer/components/SqlEditor.tsx 第 106-121 行
**对比**: src/renderer/components/ObjectExplorer.tsx 第 31-51 行（已修复，有 requestIdRef）

**问题描述**: useEffect([connectionId]) 中 fetchSchemaSnapshot(connectionId) 的 Promise 链没有 requestIdRef 守卫。快速切换连接 A→B 时：
1. A 的 fetch 慢，resolve 晚于 B 的
2. A 的 snapshot 覆盖 snapshotRef.current，但此时 connectionId 已是 B
3. 用户看到的是 A 的 schema 数据，但连接是 B 的

ObjectExplorer 已用 requestIdRef 机制修复了同类竞态，SqlEditor 未同步修复。

**修复方案**: 参考 ObjectExplorer 的做法，增加 requestIdRef 并在 then/catch 中检查。

### 🟡 [严重:低] index.ts before-quit 可能访问 undefined connectionManager

**文件**: src/main/index.ts 第 96-98 行

**问题描述**: before-quit 事件中直接调用 connectionManager.closeAll()。如果 app 在 whenReady 之前退出（异常路径如初始化失败、app.quit() 提前调用），connectionManager 仍是 undefined，会抛 TypeError: Cannot read properties of undefined (reading 'closeAll')。

**修复方案**: 改为 connectionManager?.closeAll() 安全调用。

### 🟡 [严重:低] ObjectExplorer.tsx loadColumns catch 缺少 reqId 守卫

**文件**: src/renderer/components/ObjectExplorer.tsx 第 83-84 行

**问题描述**: loadTables 的 catch（第 60 行）有 if (reqId !== requestIdRef.current) return; 保护，但 loadColumns 的 catch（第 84 行）没有，直接 setError(...)。过期请求的错误消息会覆盖后续有效请求正常加载后的状态，导致用户看到错误提示但实际数据已加载。

**修复方案**: 在 loadColumns 的 catch 中也增加 reqId 守卫。

### 🟢 [严重:低] history 中 success 语义变化：截断 = 不成功

**文件**: src/main/ipc.ts 第 157 行

**问题描述**: success: result.resultSets.every((r) => !r.truncated) 将"截断"视为"不成功"（success=false）。但执行截断 ≠ 执行失败——查询本身成功执行，只是结果集超过了 5 万行上限。这可能导致历史记录中 success=false 的含义混淆：用户看到 success=false 会以为查询执行出错，但实际上只是数据量太大被截断了。

**修复方案**: 建议将 success 语义拆分为两个字段，或保持 success=true 表示执行成功，新增 truncated 字段表示截断。

---

### 🟢 [严重:低] CSP 安全权衡

**文件**: index.html 第 8 行

**问题描述**: script-src 'self' 'unsafe-inline' 'unsafe-eval' 和 connect-src 'self' ws: http: https: 显著削弱了 CSP 纵深防御：
- unsafe-eval + unsafe-inline：允许任意代码执行
- connect-src 'self' ws: http: https: ：允许渲染进程连接任意外部 HTTP/HTTPS/WebSocket 地址，包括内网（SSRF 风险面）
- 虽然 Electron 有 contextIsolation: true 保护，但 CSP 作为纵深防御层被削弱
