## 2. 常用命令

```bash
# 安装依赖
npm install

# 开发模式：先构建主进程，再启动 Vite 和 Electron
npm run dev

# 类型检查
npm run typecheck

# 运行全部测试
npm test

# 运行指定目录/文件测试
npx vitest run tests/main/
npx vitest run tests/renderer/
npx vitest run tests/shared/
```

## 3. 构建体系

### 3.1 三类产物

| 部分 | 入口 | 构建配置 | 产物 |
|---|---|---|---|
| Main | `src/main/index.ts` | `vite.main.config.ts` | `dist/main/main.cjs` |
| Preload | `src/preload/index.ts` | `vite.main.config.ts` | `dist/main/preload.cjs` |
| Renderer | `src/renderer/main.tsx` | `vite.config.ts` | `dist/renderer/` |

`package.json` 为 ESM 项目，但 Electron 主进程和 preload 使用 CommonJS 产物，因此不要把 `.cjs` 改回 `.js`。`src/main/index.ts` 中 preload 路径必须对应 `preload.cjs`。

主进程构建会把 npm 包和 Node 内置模块 external 化。better-sqlite3 是原生模块，不能被打进 bundle。

### 3.2 别名约束

以下三处必须保持同步：`tsconfig.json`、`vitest.config.ts`、`vite.config.ts`。

```text
@/*          -> src/*
@shared/*    -> src/shared/*
@main/*      -> src/main/*
@preload/*   -> src/preload/*
@renderer/*  -> src/renderer/*
```

修改别名后必须同时运行 typecheck、测试和 Renderer 构建。

### 3.3 Monaco

Monaco 通过 npm 包本地加载，生产环境不能依赖 CDN。`src/renderer/main.tsx` 负责 loader 预热和本地 Monaco 配置；CSP、worker 和 `monaco-editor` 依赖必须一起维护。

## 4. 代码边界

### 4.1 Renderer

Renderer 只负责 UI、交互状态和纯逻辑：

- 不 import mysql2、better-sqlite3 或 Node 文件模块。
- 不读取密码、不保存解密后的连接配置。
- 不直接使用 `ipcRenderer`。
- 所有主进程能力通过 `window.sqlStudio['domain:action']()` 调用。

### 4.2 Preload

Preload 只做两件事：

1. 根据 `IPC_CHANNELS` 构造类型化 API。
2. 调用 `ipcRenderer.invoke()` 并解包统一响应。

不要在 preload 增加业务判断、数据库逻辑或文件操作。

### 4.3 Main

Main 负责：Electron 生命周期、IPC handler 注册、服务组装、数据库连接和查询、SQLite 和本地文件访问、safeStorage 加解密、AI API 调用、持久日志与崩溃事件。

### 4.4 Service

服务应尽量通过构造函数注入依赖（数据库工厂、文件系统抽象、加密函数、外部 fetch、SQLite 路径），以便在 Vitest 中用 mock 测试，不依赖真实 Electron 或真实 MySQL。

## 5. IPC 开发流程

新增或修改 IPC 时按以下顺序执行：

1. 在 `src/shared/types.ts` 增加或调整共享数据类型。
2. 在 `src/shared/ipc-contract.ts` 登记 channel、请求映射和响应映射。
3. 在 `src/main/ipc.ts` 实现 handler。
4. 必要时在 `src/main/index.ts` 注入服务实例。
5. 确认 preload 自动暴露该 channel（当前 preload 按 `IPC_CHANNELS` 自动构造，无手写方法）。
6. 在 Renderer 调用 `window.sqlStudio`。
7. 增加主进程、渲染进程或契约测试。
8. 运行 typecheck、相关测试和完整构建。

统一响应模型：

```text
Main handler 成功 -> { ok: true, data }
Main handler 失败 -> { ok: false, error, errorType? }
Preload 成功      -> Promise<data>
Preload 失败      -> rejected Error
```

channel 命名统一使用 `域:动作`，例如 `query:execute`、`favorites:list`。当前共 41 个 channel（清单见 `架构文档.md` §6）。

## 6. 数据库与查询开发

### 6.1 连接安全

`ConnectionConfig` 只能在 Main 内部使用，包含解密后的密码；`ConnectionSummary` 可以返回 Renderer，但不得包含 password。

```text
Renderer ConnectionInput -> IPC -> Security.encrypt -> SQLite connections.password
SQLite 密文 -> Security.decrypt -> Main ConnectionManager -> mysql2
```

编辑连接时 password 为空表示保留旧密码。`Security.encryptionAvailable` 可判断是否走了真加密（`b64:` 降级仅为编码）；当前 UI 未在降级时提示风险（见待办 #11）。

**解密必须按前缀分流**（`security.ts`）：`hex:` 只在 safeStorage 可用时解；`b64:` 永远走 base64 解码（**不能**交给当前加密器，否则在后来启用 safeStorage 的机器上会永久解不开）；无分隔符的历史明文原样返回。`metadata-store` 的摘要路径（`rowToSummary`）**不解密**，因此单条密文损坏不会拖垮连接列表。

### 6.2 Schema 查询

SchemaCache 对每个 connectionId 单独建立缓存（IPC 层 `Map` 持有），缓存数据库、表、字段和 DDL。所有库名、表名都必须经过反引号转义：

```ts
name.replace(/`/g, '``')
```

连接保存/删除后必须清理对应缓存。`schema:dataPreview` 当前仍单独包装 `QueryService`（见待办 #10）。

### 6.3 查询执行

查询流程由 `query:execute`、`ConnectionManager.executeMany()` 和 `QueryService.run()` 组成：

- `executeMany()` 负责 MySQL 多语句临时连接和原始结果归一化（真实 mysql2 返回 `[rowsList, fieldsList]`）。
- `QueryService` 负责列、行、截断、写操作标记和聚合耗时；`elapsedMs` 为累计耗时。
- 默认单结果集最大 50,000 行。
- 历史记录在 IPC 查询 handler 中自动写入。
- 写操作判定统一调用 `src/shared/sql-classify.ts`，Main 不信任 Renderer 的判定结果。

关键限制：普通 `query:execute` 走 `executeMany()` 的**临时多语句连接**，不是连接池（有意保留）。查询取消链路：`query:cancel` → AbortController → `makeExecutor` 透传 signal → `executeMany(signal)` → 硬销毁 stream + 本地 reject `AbortError`。

不要在没有测试的情况下修改多语句解析、结果集类型或取消机制。

### 6.4 写操作判定

已实现，位于 `src/shared/sql-classify.ts`（无 Electron 依赖，Main/Renderer 共用），覆盖 INSERT、UPDATE、DELETE、REPLACE、ALTER、DROP、TRUNCATE、CTE 包裹写、`CALL`、多语句混合、注释/字符串/括号/前置空白干扰；无法确定时按高风险处理。修改后必须同步跑 `tests/shared/sql-classify.test.ts` 与 IPC 测试。

## 7. 文件与导出开发

### 7.1 ScriptStore

`ScriptStore` 负责用户自选路径下的 SQL 文件读写。对话框由 IPC 主进程 handler 调用，Store 只负责文件 IO。当前源码已无 `window.prompt`，打开/保存/另存为全部走 `dialog:showOpenDialog` / `dialog:showSaveDialog`。

### 7.2 FavoritesStore

收藏目录为 Electron `userData/queries/`。每条收藏是一个 `.sql` 文件，文件头保存元信息：

```sql
-- name: 每日统计
-- connection: conn_xxx
-- tags: 日报, 活跃
-- createdAt: 2026-08-20T10:00:00.000Z

SELECT ...;
```

文件名必须安全化（`sanitizeFileName` 处理路径分隔符、Windows 保留设备名、纯点名、超长名），重名追加 ` (2)`、` (3)`。**读取、删除、重命名已统一走 `resolveFavoritePath`（文件名精确 + meta.name 回扫）**，不再是"规则不完全一致"的状态。

### 7.3 CSV

CSV 导出要求：

- UTF-8 BOM。
- RFC 4180 字段转义（逗号、引号、换行正确包裹）。
- 以 `= + - @` 开头的字段增加前缀，避免 Excel 公式注入。
- WritableStream 返回 false 时等待 drain，不能无视 backpressure。

### 7.4 SQL INSERT

SQL 导出必须：

- 正确处理 NULL、数字、布尔值和二进制。
- 字符串转义单引号、反斜杠、换行、回车和 NUL。
- 表名和列名使用 `escapeIdent` / `resolveTableIdent` 统一转义，并拒绝把 SQL 片段当标识符。
- `validateBatchSize` 校验 batchSize，拒绝 0、负数和非整数。

### 7.6 Excel 导出的列 key 必须用列下标

`ExcelExporter` 的 `ws.columns[].key` 与写入行对象的 key 都用 `col_${idx}`（列下标），**不能用列名**：结果集可能含同名列（如 `SELECT a.id, b.id`），用列名会让两列共享同一个 key，`addRow` 时后值覆盖前值 → 导出的两列变成同一份数据。表头文本仍显示真实列名。CSV / SQL 导出按数组下标取值，不受影响。

### 7.5 导出与文件对话框

导出、另存为共用 `dialog:showSaveDialog`；取消返回 null，不创建文件；导出后可经 `shell:showItemInFolder` 定位。路径与设置 key 的运行时校验仍待补（见待办 #12）。

**默认文件名带日期时间**：统一由 `src/renderer/lib/file-name.ts` 的 `withTimestamp(base, ext)` 生成（本地时间 `YYYYMMDD_HHmmss`，不含 `:` 字符）。三种导出与脚本另存为都走它，用户不起名时可直接回车保存。新增默认名时**不要**另写一套格式化逻辑。

## 8. 工作区恢复与持久日志开发

这两块是 2026-09-07 引入的子系统，改动时注意以下不变量。

### 8.1 自动保存

- Renderer 侧 `src/renderer/lib/workspace-persistence.ts`：500ms 防抖、结构事件立即排队、串行队列 latest-wins、最多 3 次退避重试、hydrate 屏障、退出 flush。
- **自动保存绝不调用 `script:save`、不写真实 `.sql` 文件**，只调 `workspace:save`。
- 快照只包含标签、顺序、活动标签、连接 id 等白名单字段；**不持久化** execution / results / executing，不含任何凭据。

### 8.2 恢复

- 启动时 `workspace:load` → `hydrateFromSnapshot`（显式清空 execution/results/executing）。
- 连接失效回退 null；恢复失败时以空工作区启动，不白屏。
- 坏标签隔离（单行坏不影响其余）、未知版本隔离。

### 8.3 SQLite schema 迁移

`MetadataStore` 的 schema 版本迁移必须显式、单事务、失败回滚、可重复执行（幂等）。v1→v2 新增 `workspace_snapshots` / `workspace_tabs`。`WorkspaceRecoveryStore` 与 `MetadataStore` 共用同一连接（`getSharedDatabase()` 受控注入），不要在别处新开连接。

### 8.4 持久日志

- Main 侧 `PersistentLogService` 使用 electron-log 5.4.4：`electron-log/main` 导入、自定义 `format` 输出单行 JSON、自定义 `archiveLogFn` 轮转（10 MiB / 5 归档 / 14 天 / 60 MiB）、`sync: true` 即时落盘、受控路径 `userData/logs/`、`read` 最近 500 条、`clear` 只清受控文件。
- `log-redaction` 做双层脱敏，**禁止**记录密码、API Key、完整敏感 SQL。
- Renderer 侧 `persistent-log-bridge.ts`：warn/error 即时、debug/info 批量（20 条或 250ms）、重入防护。
- Main 崩溃事件已手动注册 5 类（uncaughtException / unhandledRejection / render-process-gone / unresponsive / did-fail-load）；electron-log 官方 `eventLogger` 未启用。

### 8.5 AI 补全开发要点

- **超时必须与 Renderer 同源**：`AiService.complete()` 使用 `normalizeAiRateLimitConfig(config.rateLimit).requestTimeoutMs`，不要新增硬编码超时常量（否则设置面板调了也不生效）。
- **主进程日志不能只写 `console`**（打包后不可见、日志会丢）：`AiService` 通过构造参数注入日志出口，由 `src/main/index.ts` 接到 `PersistentLogService`（`event: ai.request`）；只落非敏感摘要（URL 摘要/协议/长度/状态码/耗时）。
- **`ai-provider` 的 `disposeInlineCompletions` 必须保持 no-op**：它是 Monaco 的**结果级回收**回调（`reason: lostRace` 等），置 `cancelled` 会让补全「触发一次后再也不触发」（详见 `架构文档.md` §5.1）。provider 生命周期只由 `dispose()` 控制。
- **限流四参数**（防抖/最小间隔/冷却/超时）来自 `AiRateLimitConfig`，缺省值与范围由 `shared/ai-protocol.ts` 统一归一化，不要在组件里写死常量。

## 10. 本地打包与发布（Windows）

### 10.1 标准流程

```bash
npm install
npm run package      # = npm run build && electron-builder --win
```

产物在 `release/`：`SQL Studio Setup 0.1.0.exe`（NSIS 安装包）+ `win-unpacked/`（免安装可运行目录）。

**本地调试优先用免安装版**（不需要任何特权，也绕开 10.3 的 winCodeSign 问题）：

```bash
npm run package:dir   # 只产出 release/win-unpacked/，直接运行 SQL Studio.exe
```

### 10.2 网络加速（可选）

registry 保持 npmmirror 直连即可（实测 0.49s，比走代理快）。只有访问 GitHub 的二进制下载需要代理：

```powershell
$env:HTTP_PROXY='http://127.0.0.1:7897'
$env:HTTPS_PROXY='http://127.0.0.1:7897'
$env:NO_PROXY='registry.npmmirror.com,npmmirror.com,localhost,127.0.0.1'
$env:ELECTRON_MIRROR='https://npmmirror.com/mirrors/electron/'
$env:ELECTRON_BUILDER_BINARIES_MIRROR='https://npmmirror.com/mirrors/electron-builder-binaries/'
```

### 10.3 已知坑位

1. **npm 11 的 allow-scripts**：`npm install` 可能跳过依赖的 install 脚本，导致 `node_modules/electron/dist` 缺失。补救：

   ```bash
   node node_modules/electron/install.js   # 带 ELECTRON_MIRROR / 代理环境变量执行
   ```

2. **winCodeSign 符号链接失败**（非管理员、未开开发者模式）：

   ```text
   ERROR: Cannot create symbolic link : 客户端没有所需的特权
   ...\winCodeSign\<随机数字>\darwin\10.12\lib\libcrypto.dylib
   ```

   该 7z 内含 macOS 符号链接，Windows 普通用户无权创建。三条出路：
   - 生成免安装可运行目录（推荐本地调试，无需任何特权）：
     ```bash
     npm run package:dir
     ```
     等价于 `electron-builder --win --dir --config.win.signAndEditExecutable=false`。若在 PowerShell 里直接敲 CLI，必须给该参数加引号（`'--config.win.signAndEditExecutable=false'`），否则 `-c.xxx` 会被当成文件路径报 `ENOENT`。
   - 开启 Windows 开发者模式（设置 → 系统 → 开发者选项），或
   - 以管理员身份运行打包命令。

3. **better-sqlite3 ABI 抖动**：`electron-builder` 会把 `node_modules/better-sqlite3/build/Release/*.node` 重建为 Electron ABI，此后直接跑 `npm test` 会报 ABI 不匹配。恢复：

   ```bash
   npm rebuild better-sqlite3
   ```

4. **`.npmrc` 的 `electron_mirror` / `binary_host_mirror`**：npm 11 起会告警"Unknown project config"，建议改用上面的环境变量方式。

### 10.4 CI

`.github/workflows/build.yml` 在 push/PR 到 `master`/`main` 时构建 Windows + Linux 产物，也支持手动触发（`workflow_dispatch`）。本地打包成功后无需再依赖 CI。

## 11. 调试与排错

### 11.1 Electron 启动失败

依次检查：`npm run typecheck` → `npm run build:main` → `dist/main/main.cjs` 与 `dist/main/preload.cjs` 是否存在 → preload 路径是否使用 `.cjs` → 开发模式 Vite 是否监听 5173。

### 11.2 IPC 无 handler

检查：channel 是否在 `IPC_CHANNELS` 登记 → 请求/响应 map 是否登记 → `registerIpc()` 是否在 `app.whenReady()` 中调用 → handler 是否被重复注册 → preload 是否读取同一份 `IPC_CHANNELS` → IPC 测试是否覆盖。

### 11.3 better-sqlite3 加载失败

```text
was compiled against a different Node.js version
Module did not self-register
```

原因是 Node ABI、Electron ABI 或现有 `.node` 文件不匹配。优先 `npm run rebuild`（针对 Electron）或 `npm rebuild better-sqlite3`（针对 Node）。测试中的 `store.close()` 二次报错通常是构造函数已经因原生模块加载失败，不能把它当成根因。

### 11.4 查询取消无效

检查完整链路：

```text
App clientQueryId -> query:execute -> queryAborters Map -> QueryService signal
  -> makeExecutor(signal) -> ConnectionManager.executeMany(signal) -> mysql connection destroy
```

任何一层不传 signal，停止按钮都可能只改变 UI 状态而不能中断数据库查询。

### 11.5 打包后应用启动异常

- 确认 `release/win-unpacked/resources/app.asar` 存在且体积正常。
- 查看 `%APPDATA%\SQL Studio\logs\main.log`（持久日志会记录启动与崩溃事件）。
- 原生模块问题优先按 11.3 处理。

## 12. 维护规则

1. 不在 `src/main`、`src/preload`、`src/renderer` 重复定义共享类型。
2. 不在 Renderer 直接访问 Node 或数据库。
3. 不把密码、API Key、完整敏感 SQL 写入日志。
4. 不把 `.bak` 文件当作正式源码引用。
5. 不用历史文档中的测试数量替代实际命令输出。
6. 新增功能必须同时补测试。
7. 数据库、文件、加密、连接池变更先做小范围验证，再进行全量验证。
8. 修改前检查 `git status` 和 `git diff`，不覆盖用户已有改动。
9. 不通过重装依赖或清理目录解决问题而不记录原因。
10. 文档更新必须反映实际代码，不得把规划功能写成已完成。
11. 待办只写在 `docs/待办与遗留问题.md`，其他文档不重复维护待办列表。

## 13. 完成验收标准

任何代码变更完成前，至少满足：

```bash
npm run typecheck
npm test
npm run build
```

涉及 Electron、MySQL、文件对话框或查询取消时，还要执行对应的端到端冒烟测试（见 `e2e-checklist.md`），并记录：修改文件、行为变化、测试命令和结果、已知限制、是否需要迁移或回退。

只有三条基础命令和必要的功能验证全部成功，才能在架构文档中标记为完成。
