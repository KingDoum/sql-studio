## 2. 分层与边界：结论与证据

### 2.1 进程边界（✅ 无违规）

| 检查项 | 结果 | 判定 |
|---|---|---|
| Renderer 引用 `@main` / `../main` | **0** | ✅ |
| Renderer 引用 `node:*` | **0** | ✅ |
| Main 引用 `@renderer` | 1 处，是 `index.ts:116` 的 `win.loadFile(path.join(__dirname,'../renderer/index.html'))` | ✅ 属**构建产物的运行时路径**，非源码依赖 |
| Shared 引用 `electron` / `@main` / `@renderer` | 2 处，均为注释（"无 Electron 依赖"） | ✅ 真实引用 0 |
| Preload 引用 `services/` | **0** | ✅ preload 纯转发 |
| 谁 import `electron` | 仅 `main/index.ts`、`main/ipc.ts`、`preload/index.ts` | ✅ 边界收敛 |

> 这个结果比预期好：`preload/index.ts` 只有 49 行且不含业务判断，`shared/` 真正做到零依赖（可被任何进程引用），这是**可以把纯逻辑放 shared 的前提**。

### 2.2 服务层切分（✅ 合理）

`index.ts` 只做生命周期与服务组装，`ipc.ts` 已经拆成「组装 + 按域 handler + 共享依赖」四件套：

```text
ipc.ts (40 行，只注册)  ←  ipc-deps.ts (118 行，Dep 接口 + 跨域校验)
                          ←  ipc-handlers-db.ts  (连接/Schema/查询/历史)
                          ←  ipc-handlers-io.ts  (脚本/导出/收藏/对话框)
                          ←  ipc-handlers-app.ts (应用/AI/设置/工作区/日志)
```

这是比「一个 387 行的 ipc.ts」明显更好的结构，**且已被 `tests/main/ipc.test.ts` 覆盖**。

### 2.3 依赖注入（✅ 到位）

`ConnectionManager(factory)`、`QueryService(executor)`、`SchemaCache(executor)`、`MetadataStore(path, factory?)`、`ExcelExporter(workbookFactory)`、`AiService(..., logSink?)` 都是构造注入。直接收益：**14 个 service 全部有单测，且测试不连 MySQL、不需要 Electron**。这是本项目最值得保持的设计决策。

## 3. 发现的问题（按优先级，含证据与建议）

### ✅ P1-1（已修复）：标识符转义曾有 3 处实现，且**同名函数语义不同**

| 位置 | 签名 | 实际行为 |
|---|---|---|
| `main/services/sql-exporter.ts:42` | `escapeIdent(name)` | **转义 + 反引号包裹** → `` `a``b` `` |
| `renderer/lib/sql-utils.ts:112` | `escapeIdent(name)` | **只转义，不包裹** → `` a``b `` |
| `main/services/schema-cache.ts:32` | `esc(name)` | 只转义，不包裹（与上一条逻辑完全相同，仅名字不同） |

**风险**：
1. **命名陷阱**：两个 `escapeIdent` 名字一样、语义差一层反引号。后续有人跨层复制代码，会得到多一层或漏一层的引号 → SQL 语法错误或（更坏）注入面扩大。
2. **安全相关逻辑分散**：转义是 SQL 注入防线的最后一环，散在 3 个文件意味着"修一处漏两处"。
3. `sql-exporter.ts:52 resolveTableIdent` 额外做了「拒绝 `;()\n\r`」的片段校验，而另两处没有——**渲染进程拼 `buildSelectSql` 时没有这层校验**。

**已实施（2026-09-17）**：新建 `src/shared/sql-ident.ts`，导出 `escapeIdentRaw`（只转义）/ `quoteIdent`（转义 + 反引号包裹）/ `quoteQualifiedIdent`（解析 `db.table` 并拒绝 SQL 片段）。`sql-exporter`、`schema-cache`、`sql-utils` 三处调用点全部改为引用共享实现；补 `tests/shared/sql-ident.test.ts` **12 例**，覆盖反引号转义、包裹、点号、空段、三段、空串、以及 `;` / `()` / 换行片段的拒绝。

### ✅ P1-2（已修复）：列类型归一化曾有 2 处实现，且**行为不一致（用户可见）**

| 位置 | 差异 |
|---|---|
| `main/services/schema-cache.ts:45 normalizeType` | `text` → `'text'`；**longblob 会落到 `'blob'`** |
| `main/services/query-service.ts:172 normalizeType` | 多了特例：`t.includes('text') \|\| (t.includes('blob') && t.includes('long'))` → `'text'` |

**影响**：同一个 `longblob` 列，在**左侧对象浏览器的字段列表**里显示 `blob`，在**查询结果网格的表头**里显示 `text`。用户看到同一列两个类型名，会怀疑哪个是真的。

另外 `query-service.ts:145` 还有第三份映射 `mysql2TypeToName(code)`（把 mysql2 的数字类型码转名字），它和 `normalizeType` 的字符串分支**必须保持同步**，但目前没有任何机制保证——两处注释都没写这条约束。

**已实施（2026-09-17）**：`columnTypeFromCode` / `columnTypeFromRaw` 已收敛到 `src/shared/column-type.ts`，`query-service`（结果集表头）与 `schema-cache`（字段列表）两处调用点改引用。

**口径统一为 `longblob` → `blob`**：理由有二 —— ① mysql2 类型码路径本就把 249~252（tinyblob/blob/mediumblob/longblob）全部映射为 `blob`，字符串路径应与之一致；② 二进制列不该标成文本。

测试覆盖 blob 家族、日期时间优先级（`datetime` 先于 `date`、`timestamp` 先于 `time`）、长度/unsigned 修饰、未识别类型原样返回；并**显式记录了一条既有口径**（含 `int` 子串的类型会归 `int`，如 `point`/`linestring`），避免将来有人"顺手修"导致行为静默变化。

### 🟠 P2-1：未使用依赖 `tdesign-react`

- `package.json` 的 `dependencies` 里声明了 `"tdesign-react": "^1.9.3"`，`node_modules` 里也装了
- **`src/` 中 import 次数：0**（全 UI 由自研组件 + lucide-react 构成）
- `docs/开发文档.md` §1.2 把它列为技术栈「UI 组件」→ **文档与实现不符**
- 它在 `dependencies` 而非 `devDependencies`，因此**会被打进安装包**（体积与供应链面双双增加）

**建议**：确认无隐藏运行时用法后移除该依赖，并同步删掉开发文档技术栈表格里的那一行。

### 🟠 P2-2：4 个巨型文件

| 文件 | 行数 | 说明 |
|---|---|---|
| `renderer/styles/theme.css` | 3,369 | 单文件 18 个小节。**但**：它是纯样式且有清晰的分节注释，改样式时按节定位即可，优先级最低 |
| `renderer/App.tsx` | 750 | 编排组件。同时持有 20+ 个 `useState`、查询执行、文件打开保存、收藏/历史/主题/外观等所有面板的开关 |

`App.tsx` 是**唯一有实际维护风险**的一个：它把「面板开关编排」和「查询/文件业务流程」混在一起，`待办与遗留问题.md` #16 已记录拆分诉求。建议拆成 3 个 hook：`useQueryExecution` / `useFileOps` / `usePanels`，App 只保留 JSX 与状态装配。
`SqlEditor` 可把 AI provider 相关（`syncAiProvider` + 生命周期 ref）抽成 `useAiInlineProvider`。

### 🟡 P3-1：唯一无测试引用的组件

`renderer/components/TableFieldsPanel.tsx`（245 行）——全项目**唯一**没有任何测试引用的模块（`lib/`、`store/` 全部有覆盖）。它包含「从 SQL 里解析出引用的表」这条不平凡逻辑（含子查询、跨库），建议至少补：缓存键（`db.table` 不含连接维度）、连接切换清缓存、加载失败回退。

> `main/ipc-handlers-*.ts` 与 `ipc-deps.ts` 也没有**独立**测试文件，但它们被 `tests/main/ipc.test.ts` 实际执行，属可接受。若要更稳，可给 handler 的**输入校验分支**单独加用例。

### 🟡 P3-2：`app-store` 之外的全局耦合

`renderer/` 中 `window.sqlStudio` 直接调用 **66 处**。这是架构允许的唯一桥（preload 自动暴露），但 66 处散落意味着**改返回结构要全局搜索**。可选改善：按域包一层 `renderer/lib/api.ts`（`api.query.execute(...)`），把 66 处收敛成 1 个类型安全入口，测试也可只 mock 一处。

### ✅ 值得保持的做法（评审中确认的正面项）

1. `shared/` 零依赖，且 `sql-classify` / `column-type` / `ai-protocol` 被 Main 与 Renderer **共用同一实现**（"判两遍"是明确禁止的反模式，这里做对了）。
2. IPC 响应统一 `{ok,data}` / `{ok:false,error,errorType}`，preload 解包，Renderer 只拿到裸数据或 rejected Error。
3. `resolveFavoritePath` 统一收藏定位、`withTimestamp` 统一默认文件名、`escapeIdent` 统一转义——**每个"曾经不一致"的点都收敛成单一来源**（本轮新发现的两处是这个原则的漏网之鱼）。
4. `MetadataStore` 的 `rowToSummary`（不解密）/ `rowToConfig`（隔离坏密文）双路径，避免单条坏数据拖垮整个列表。
5. 迁移显式、单事务、幂等；快照字段白名单不含凭据。
6. 日志双层脱敏 + 主动不用 electron-log 的 `eventLogger`（因为它绕过脱敏链路）。

### 4.4 文档体系缺什么（本次补上）

原文档回答的是**"系统是怎么设计的"**（架构文档）和**"流程怎么走"**（开发文档）。但你的核心诉求是**"我要改某个模块时，怎么快速知道该动哪些文件、不能碰什么、跑哪些测试"** —— 这个视角原先没有文档承载，只能靠通读 11,947 行源码。

因此新增 **`模块改动指南.md`**：

- **§1 需求 → 模块索引**：14 类常见改动，每类给出「主改文件 / 必须同步改的地方 / 该跑哪些测试」
- **§2 模块卡片**：按层给出每个模块的职责、依赖、**不变量（改动红线）**、改动检查单、覆盖测试、已知坑
- **§3 高危改动清单**：10 项必须谨慎的改动（转义、取消链路、密码分流、Excel 列 key、自动保存不写文件、Monaco 语义……）
- **§4 验证命令速查**

### 4.5 建议的文档维护规则（补充到开发文档 §12）

1. **数字只在一处维护**：channel 数量、文件行数这类会漂移的数字，只写在 `架构文档.md`，其他文档引用而不复述。

4. **收敛类改动（把重复实现合成单一来源）要在指南的"高危清单"里留一条**，防止后人再复制出去。
